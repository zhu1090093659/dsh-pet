宠物插件随 dsh-web 家族对齐到统一版本 0.4.19，与全家桶 0.4.19 同版本发布。本区间 `v0.4.18..HEAD` 只有一条提交（`a465df5 feat(pet): add plugin page display metadata`），给插件列表页补上显示元数据：新增 `locale/en.json` 与 `locale/zh.json`，各自带 `meta.title` 与 `meta.description`；`package.json` 为这两个文件加上 `./locale/en.json`、`./locale/zh.json` 两条导出键，并把 `locale` 目录写进 `files` 白名单；另加 `tests/display-metadata.spec.ts`，把这条通道钉成有断言的契约。宠物本身的行为没有任何变化：没有新增宠物、没有新增或改动设置项，渲染器、游戏逻辑、拖拽、亲和度与冷却账本、线协议字段与持久化标识一个都不动。用户能看见的差别只有一处——宿主插件列表里的这一行不再退回 npm 包名与英文 manifest 描述，而是显示本包自带的中英文标题与短描述（英文 `Desktop pet` / `An interactive pet on the desktop.`，中文 `桌面宠物` / `桌面上的互动宠物`）。

> **兼容性**：没有破坏性变更，依赖、peer 与 engines 一行未改——`dsh.engines.dsh` 与 `@deepseek-ai/dsh` 的 peer 下限仍是 `>=0.2.2-rc.2`，`engines.node` 仍是 `>=24.9.0`，停在 0.4.18 的安装可以直接升上来，也可以直接退回去，两个方向都不需要迁移数据。包名 `@linxin666/dsh-pet` 与安装方式不变；持久化标识不变（布局与游戏进度仍写在 `$DSH_HOME/pet.json`，键名一个不改；宠物资产仍落在 `$DSH_HOME/pets/<id>/`；语音包分层仍是宠物 `voice.json` > 全局 `$DSH_HOME/pets/.voice.json` > 内置）；状态装饰目录与 `decoration.json` 契约不变；线协议字段与设置字段名（`petId`、`statusBubbles` 等）不变。导出面只新增两个子路径，已有的 `.`、`./client`、`./src/*`、`./package.json` 一条不改，所以既有子路径导入不会失效，旧文件也不会被 `exports` 白名单挡掉；`icon` 字段与 `icon.svg` 在 v0.4.18 就已存在，本区间一个字节没动。不读这条通道的宿主对新增导出键没有任何调用点，升级对它们等价于只换了个版本号。

### 新功能

- 插件页显示元数据（`a465df5`）：npm 包清单自带的 `description` 只有一句英文、标题只能落到包名，插件列表因此一直显示 `@linxin666/dsh-pet` 与那句英文描述。本版补上宿主已经在读的本地化通道：
  - `locale/en.json`：`meta.title` 为 `Desktop pet`，`meta.description` 为 `An interactive pet on the desktop.`
  - `locale/zh.json`：`meta.title` 为 `桌面宠物`，`meta.description` 为 `桌面上的互动宠物`
  - `package.json` 的 `exports` 增加 `./locale/en.json` 与 `./locale/zh.json` 两条映射，`files` 白名单增加 `locale` 目录
- 三处必须在场，缺一不可：宿主先解析 `locale/en.json`，再枚举该目录下每个 `*.json` 并经本包自己的 `exports` 映射逐个解析。文件在而导出键缺、导出键在而文件缺、或者 `locale` 目录被 npm 的 `files` 白名单漏掉（打包时整个目录不进 tarball），任何一种都会让整次元数据读取失败，页面静默退回包名与英文描述，且不给任何报错
- 影响面只在显示层：宠物注册表、渲染、拖拽、交互与持久化一条都不经过这条通道，运行时行为与 0.4.18 逐条一致
- 文案本身也受约束：中文标题与描述必须与英文不同，中文描述的汉字数不超过 20，两条标题都非空——这几条写在测试里，不是口头约定

### 修复

- 无缺陷修复：本区间唯一的提交只新增两份 locale 文件、两条导出键、一条 `files` 条目与一支测试，没有一行改动既有行为代码、资产或契约

- 该测试同时被两道门覆盖：`pnpm test`（`vitest.config.ts` 的 `tests/**/*.spec.ts`）与 `pnpm typecheck`（`tsconfig.test.json` 的 `tests/**/*.spec.ts`），`pnpm build` 不把它打进 `lib/`

- 版本对齐：`package.json` 的 `version` 从 0.4.18 改为 0.4.19，跟随 dsh-web 家族的统一版本线；卫星先发、主仓随后跟上同号
- 发布产物：`locale/` 是静态内容，原样进入 tarball，不经构建；`lib/` 仍不入库（在 `.gitignore` 里），发布时由 `prepare` 脚本现场重建
- 构建期唯一随版本变化的烙入值是 `shared/tsdown.client.ts` 的 `buildPackageVersion()`：它读 `version` 并作为 `__DSH_PKG_VERSION__` 烙进匿名安装心跳，烙入值从 0.4.18 变成 0.4.19；压缩后的模块体、导出表与类型声明由上面那次提交决定

- 行为不变量：宠物渲染与拖拽位置、亲和度积分、奖励、冷却与已持久化的账本、设置表单与公告位、配对信任围栏、注册表扫描语义都与 0.4.18 完全一致；`src/`、`assets/` 与 `contracts/` 相对 0.4.18 一个字节没动

The pet plugin aligns with the unified dsh-web family version 0.4.19, on the same version as the family's 0.4.19. The range `v0.4.18..HEAD` holds a single commit (`a465df5 feat(pet): add plugin page display metadata`), which gives the plugin list page its display metadata: `locale/en.json` and `locale/zh.json` are added, each carrying `meta.title` and `meta.description`; `package.json` gains the `./locale/en.json` and `./locale/zh.json` export keys for those two files and lists the `locale` directory in its `files` whitelist; and `tests/display-metadata.spec.ts` turns that channel into an asserted contract. The pets themselves do not change: no pet is added, no setting is added or changed, and the renderers, gameplay logic, dragging, affinity and cooldown ledgers, wire-protocol fields and persistence identifiers are untouched. Exactly one difference is visible to users - the row in the host's plugin list no longer falls back to the npm package name and the English manifest description, but shows the title and short description this package now ships in both languages (English `Desktop pet` / `An interactive pet on the desktop.`, Chinese `桌面宠物` / `桌面上的互动宠物`).

> **Compatibility**: nothing breaks, and no dependency, peer or engine line moves - `dsh.engines.dsh` and the `@deepseek-ai/dsh` peer floor stay at `>=0.2.2-rc.2`, `engines.node` stays `>=24.9.0`, so an installation on 0.4.18 upgrades and rolls back without any data migration in either direction. The package name `@linxin666/dsh-pet` and the install path are unchanged; every persistence identifier keeps its name (layout and gameplay progress still live in `$DSH_HOME/pet.json` with identical keys, pet assets still land in `$DSH_HOME/pets/<id>/`, and voice-pack layering is still pet `voice.json` > global `$DSH_HOME/pets/.voice.json` > built-in); the status-decoration directory and the `decoration.json` contract are unchanged; wire-protocol fields and the settings field names (`petId`, `statusBubbles` and the rest) are unchanged. ### New Features

- Plugin page display metadata (`a465df5`): the npm manifest description is one English sentence and the title can only fall back to the package name, so the plugin list used to render `@linxin666/dsh-pet` plus that sentence. This release fills in the localization channel the host already reads:
  - `locale/en.json`: `meta.title` is `Desktop pet`, `meta.description` is `An interactive pet on the desktop.`
  - `locale/zh.json`: `meta.title` is `桌面宠物`, `meta.description` is `桌面上的互动宠物`
  - `package.json` gains the `./locale/en.json` and `./locale/zh.json` entries under `exports`, and the `locale` directory under `files`
- All three pieces have to be present at once: the host resolves `locale/en.json` first, then enumerates every `*.json` in that directory and resolves each one through this package's own `exports` map. A file without its export key, a key without its file, or a `locale` directory that npm's `files` whitelist drops (the whole directory then misses the tarball) makes the entire metadata read fail, and the page silently falls back to the package name and the English description with no error anywhere
- The blast radius stays in the display layer: the pet registry, rendering, dragging, interaction and persistence never touch this channel, so runtime behaviour matches 0.4.18 line for line
- The copy itself is constrained too: the Chinese title and description must differ from the English ones, the Chinese description stays within 20 Han characters, and neither title may be empty - all of that lives in the test rather than in an informal agreement
