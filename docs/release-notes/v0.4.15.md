宠物插件随 dsh-web 家族对齐到统一版本 0.4.15，本区间 `v0.4.14..v0.4.15` 的两条提交把宿主 cohort 从 0.2.1-rc.3 抬到 0.2.2-rc.1：一条修好扩展页在 Cordis 4.1 新泛型事件签名下的类型兼容，一条把 SDK 依赖、锁文件、供应链豁免清单与 README 徽章一起对齐到 0.2.2-rc.1，最后是本次版本号。没有新增宠物、没有新增设置项，渲染与游戏逻辑不动。

> **兼容性**：没有破坏性变更，但宿主与 Node 的下限本轮抬高。`dsh.engines.dsh` 从 `>=0.2.1-rc.3` 抬到 `>=0.2.2-rc.1`，`@deepseek-ai/dsh` 的 peer 依赖同步抬到 `>=0.2.2-rc.1`，仍停在 0.2.1-rc.3 宿主上的安装需要先把宿主升到 0.2.2-rc.1 或更高；`engines.node` 由 `^22.19.0 || >=24.0.0` 收紧为 `>=24.9.0`，Node 22 不再被支持。包名 `@linxin666/dsh-pet` 与安装方式不变；持久化标识不变（布局与游戏进度仍写在 `$DSH_HOME/pet.json`，键名一个不改；宠物资产仍落在 `$DSH_HOME/pets/<id>/`；语音包分层仍是宠物 `voice.json` > 全局 `$DSH_HOME/pets/.voice.json` > 内置）；状态装饰目录与 `decoration.json` 契约不变；线协议字段与设置字段名（`petId`、`statusBubbles` 等）不变。宿主自身的运行时在 0.2.2-alpha.3 与 0.2.2-rc.1 之间没有差异（决策记录已核对两棵源码树一致），所以对已经在 0.2.2 系列宿主上的安装，本次只是依赖与声明跟进，行为不变；回退到 0.4.14 也不需要迁移数据。

### 修复

- 扩展页事件签名适配 Cordis 4.1：`src/client/web-extension-page.ts` 里的 `WebExtensionPageContext.on` 原先声明为宽泛的字符串事件签名（`on?(event: string, listener: () => void)`），与 Cordis 4.1 的泛型 `on` 方法结构不兼容，新 cohort 下客户端类型检查直接失败；现在把形参类型擦为 `never`，并在订阅调用点就地断言事件名与回调。事件名 `slots/changed` 与回调逻辑一个字没改，页面仍然在每次事件时重建一次设置入口，运行时行为与 0.4.14 逐条一致
- 该修复只替换两行（一处接口声明、一处订阅调用），不新增依赖，不改导出面，也不改变 slot 注册与清理时序

This release aligns the pet plugin with the unified dsh-web family version 0.4.15. Across `v0.4.14..v0.4.15` two commits move the host cohort from 0.2.1-rc.3 to 0.2.2-rc.1: one repairs the extension page's type compatibility with Cordis 4.1's new generic event signature, and one advances the SDK dependencies, lockfile, supply-chain exclusion ledger and README badges to 0.2.2-rc.1, followed by this version bump. No pet is added, no setting is added, and rendering and gameplay logic are untouched.

> **Compatibility**: nothing breaks, but the host and Node floors do move this cycle. `dsh.engines.dsh` rises from `>=0.2.1-rc.3` to `>=0.2.2-rc.1` and the `@deepseek-ai/dsh` peer dependency rises with it, so an installation still on a 0.2.1-rc.3 host needs the host upgraded to 0.2.2-rc.1 or newer first; `engines.node` tightens from `^22.19.0 || >=24.0.0` to `>=24.9.0`, which drops Node 22. The package name `@linxin666/dsh-pet` and the install path are unchanged; every persistence identifier keeps its name (layout and gameplay progress still live in `$DSH_HOME/pet.json` with identical keys, pet assets still land in `$DSH_HOME/pets/<id>/`, and voice-pack layering is still pet `voice.json` > global `$DSH_HOME/pets/.voice.json` > built-in); the status-decoration directory and the `decoration.json` contract are unchanged; wire-protocol fields and the settings field names (`petId`, `statusBubbles` and the rest) are unchanged. The host runtime itself is identical between 0.2.2-alpha.3 and 0.2.2-rc.1 (the decision record verified that both source trees match), so an installation already on a 0.2.2-series host sees a dependency and declaration follow-up with no behaviour change, and going back to 0.4.14 needs no data migration either.

### Bug Fixes

- Extension-page event signature adapted to Cordis 4.1: `WebExtensionPageContext.on` in `src/client/web-extension-page.ts` was declared with a broad string event signature (`on?(event: string, listener: () => void)`), which is not structurally compatible with Cordis 4.1's generic `on` method, so client typechecking failed outright on the new cohort; the parameter types are now erased to `never` with the event name and callback asserted at the subscription site. The event name `slots/changed` and the callback logic are untouched, the page still rebuilds its settings entry once per event, and runtime behaviour is identical to 0.4.14
- That fix replaces two lines (one interface declaration, one subscription call), adds no dependency, leaves the export surface alone, and does not change slot registration or cleanup ordering

### Other Changes

- Host cohort: SDK development dependencies move from `^0.2.1-rc.3` to `^0.2.2-rc.1` (with a stop on `^0.2.2-alpha.3` on the way), Cordis from `~4.0.5` to `~4.1.0` (via `~4.0.6-alpha.2`), and schemastery from `~3.18.5` to `~3.19.0` (via `~3.18.6-alpha.2`); `dsh.engines.dsh` and the peer floor move to `>=0.2.2-rc.1` in the same step
- Node floor: `engines.node` tightens to `>=24.9.0`, and `node-version` in `.github/workflows/ci.yml` and `.github/workflows/release.yml` moves from 22 to 24.9.0 so the gates run on the runtime the release pipeline actually uses
- Lockfile and supply-chain policy: `pnpm-lock.yaml` is re-resolved with the cohort; `packageExtensions` and `minimumReleaseAgeExclude` in `pnpm-workspace.yaml` are rewritten from `*-alpha.2` / `*-alpha.3` prefixes into exact `0.2.2-rc.1` entries, with vendor versions pinned to stable releases (Cordis 4.1.0, `cordis-plugin-loader` 1.1.0, Cosmokit 1.9.0, schemastery 3.19.0), so `pnpm install --frozen-lockfile --ignore-scripts` still passes the release-age check
- Documentation: the DSH badge in `README.md` / `README.zh.md` moves from `>=0.2.1-rc.3` to `>=0.2.2-rc.1`, the pairing hashes in `README.i18n.yaml` are re-recorded with it, and the two languages stay equivalent
- Decision records: `.agents/notes/implemented/process/2026-11-03-sdk-cohort-0.2.2-alpha.3.md` and `.agents/notes/implemented/process/2026-11-04-sdk-cohort-0.2.2-rc.1.md` record why each cohort move happened, the rejected alternatives (keeping the string signature, relying on semver to span versions, disabling the release-age policy globally, publishing a new version along the way) and the consequences
- Version alignment: `version` in `package.json` moves from 0.4.14 to 0.4.15 to follow the unified dsh-web family version (satellites ship first, the main repository follows), matching the parent repository exactly
- Exactly one difference in the published artifact comes from build time: `buildPackageVersion()` in `shared/tsdown.client.ts` reads `version` and injects it as `__DSH_PKG_VERSION__` for the anonymous install heartbeat, so the baked value changes from 0.4.14 to 0.4.15 while the minified module bodies, the export tables and the type declarations are determined by the two cohort commits above
- No committed artifact moves with it: `lib/` is not tracked (it sits in `.gitignore`) and is rebuilt on the spot by the `prepare` script at publish time, so this release commit contains only `package.json` and this file; this notes file is outside the npm package's `files` whitelist and never reaches the published artifact
- Behaviour invariants: pet rendering and dragged positions, affinity points, rewards, cooldowns and the persisted ledger, the settings form and the announcement slot, the pairing trust fence and the registry scan semantics are all identical to 0.4.14; apart from those two type-declaration lines `src/` is byte-identical to 0.4.14, and `assets/` and `contracts/` are untouched
